Todo list:

DONE - checked ^R across the ports after a windows user reported "Ctrl R exits
me from CPM" in z80cpmw. nothing here exits on ^R: there is no UI layer, no
menus, no accelerators, no key polling in the run loop, and no signal handler
anywhere (zero hits for signal(, SIGINT, SetConsoleCtrlHandler). POSIX raw mode
clears ICANON, which is exactly the flag that disables the tty's own ^R
(VREPRINT). at the three unbuffered read sites - BDOS 1, BDOS 6 and BIOS CONIN -
a typed 0x12 is masked & 0x7F and handed straight to the guest.

  CORRECTED - and this is now the reason to keep the note. the sweep said "the
  only input-side control-character test in the whole file was ch == 0x03", and
  that was never true: it covered the three unbuffered reads and missed the
  buffered one. BDOS fn 10 tested six more control characters (CR, LF, RUB, ^H,
  ^U, ^C, ^Z) and then discarded every other one under a "// Ignore other
  control characters" comment, so a typed ^R at a fn 10 prompt was dropped on
  the floor on all three platforms - exactly the class of bug the sweep was
  hunting. the fn 10 entry below is that bug. "nothing to fix for ^R" was wrong
  when it was written, and is true now only because that editor was rewritten.

  ^R is also no longer one thing across the ports. at a fn 10 prompt a typed ^R
  is now deliberately consumed as retype-line and never reaches the guest, which
  is correct CP/M and is documented in README.md under Console and Keyboard. on
  windows PgUp synthesizes 0x12, and the editor's `synthesized` guard sends that
  past retype-line and into the guest. so on windows PgUp and a typed ^R are not
  interchangeable, and anyone re-running this sweep has to test both.

DONE - the same bug with a different letter. five consecutive ^C called exit(0)
with no way to turn it off, and WordStar binds ^C to page-down, so five page-
downs in a row killed the emulator and lost the unsaved document. now
switchable the way z80cpmw fixed ^R: a ctrl_c_exit config directive, and
--ctrl-c-exit / --no-ctrl-c-exit in the option loop, feeding a static bool that
check_ctrl_c_exit tests before the exit(0). the CLI flag outranks the config
file. default stays on - a raw-mode CLI emulator does need an escape hatch. the
five also have to land within two seconds of the FIRST one, measured across the
whole run rather than keystroke to keystroke, so page-downs arriving at a
reading pace never accumulate. that window is a second line of defence, not the
fix: a fast reader can still page five times in two seconds. the switch is the
fix. documented in README.md under Console and Keyboard.

DONE - IEXTEN is now cleared in POSIX raw mode. on linux it was inert without
ICANON, but BSD/XNU gates VLNEXT (^V) and VDISCARD (^O) on IEXTEN alone,
outside the ICANON block, so the macOS build was losing ^V and ^O to the line
discipline. also picked up the ISTRIP/BRKINT/PARMRK/IGNBRK clears we were
skipping. wrote the flags out by hand instead of calling cfmakeraw().
deliberately did NOT take cfmakeraw's c_cflag CSIZE/PARENB/CS8 clear: c_cflag
is inert on a pty or a pipe, and on a real serial console it reprograms the
line itself - forcing 8N1 on a terminal someone brought up 7E1 garbles the
session. clearing ISTRIP is what actually keeps the 8th bit.

  CORRECTED - the reason first recorded for skipping cfmakeraw, "gated behind
  __USE_MISC / _DARWIN_C_SOURCE and we build strict -std=c++11", is wrong for
  both builds in the tree. g++ predefines _GNU_SOURCE=1 for C++ whatever -std
  says, so __USE_MISC is defined and cfmakeraw compiles clean under -std=c++11;
  checked by compiling a two-line program that calls it. and the cmake build is
  not strict c++11 in the first place - CMakeLists.txt sets CMAKE_CXX_STANDARD
  11 with no CXX_EXTENSIONS OFF, which cmake turns into -std=gnu++11. the
  hand-written flags stay, on the c_cflag argument above: that one is real, and
  it does not depend on what any header chooses to expose.

  worth spelling out, because the file otherwise reads as contradicting itself:
  every read site masks & 0x7F on the way into the guest, so clearing ISTRIP
  does not put an 8-bit byte in register A. it is still observable, because the
  dispatch runs on the raw byte before that mask. with ISTRIP set, an 8-bit 0x8D
  would arrive as CR and silently submit a half-typed fn 10 line, and 0x83 would
  read as ^C and count toward the five-^C exit.

DONE - ENABLE_QUICK_EDIT_MODE is now cleared, with ENABLE_EXTENDED_FLAGS set in
the same call so the bit is honoured, and ENABLE_MOUSE_INPUT cleared with it.
a stray mouse click no longer starts a selection that freezes guest input until
Esc, and ^C no longer gets stolen by windows terminal's copy binding in that
state. the restore path needs ENABLE_EXTENDED_FLAGS too or the user is left
with quick edit off after we exit. both bits have #ifndef fallbacks for older
mingw wincon.h.

DONE - the second _getch() call for extended keys. _getch signals an extended
key by returning 0x00 or 0xE0 and requiring a second call for the scan code; we
never made it, and the `ch & 0x7F` mask turned the 0xE0 into 0x60, so an arrow
key injected a backtick plus a letter into the guest. now translated to the
WordStar diamond (arrows, Home, End, PgUp, PgDn, Insert, Delete, ctrl+left,
ctrl+right) through a table, with the second byte of a two-character translation
queued and reported by stdin_has_data(). three things fell out of it:
  - Insert maps to ^V, which is the only way a WordStar user on windows terminal
    can reach insert/overtype at all (see below).
  - PgDn maps to ^C, so console_last_char_synthesized() exists to keep a
    translated page-down from counting toward the ^C exit. the fn 10 line editor
    consults it too, or a Down arrow would cancel the line being typed.
  - the second _getch() is gated on _kbhit(), because 0xE0 is a legitimate
    character in every OEM code page and an unconditional second read would
    block on one.

  CORRECTED - an earlier draft of this entry said the table covers
  "ctrl+arrows". it covers the horizontal pair only, ctrl+left -> ^A and
  ctrl+right -> ^F. ctrl+up and ctrl+down are not in it, so they miss the
  lookup, come back as a synthesized 0, and are swallowed - the user sees
  nothing at all. README.md already lists only the two, so the docs were right
  and this note was not.

DONE - the BDOS fn 10 line editor was dropping about twenty control characters,
not the handful the comment implied. it now consumes only what real CP/M 2.2
RDBUF consumes - CR LF RUB ^H ^E ^P ^R ^S ^U ^X - and stores and echoes
everything else as ^x, TAB and ESC included, so ESC-to-cancel and embedded tabs
reach the guest. ^R retype-line, ^E physical newline, ^X delete-line and ^P
printer-echo are implemented. ^C keeps landing in the buffer rather than warm
booting, because a warm boot here is program termination and the five-^C hatch
already covers the escape case. a full buffer ends the read again, the same as
a CR, which a first cut of this had regressed.

DONE - ^V on the shipped windows package is documented as a known limitation.
windows terminal binds ctrl+v to Terminal.PasteFromClipboard and it does not
fall through to the app (microsoft/terminal#16280, still open), and no
SetConsoleMode call we make can change that. a fragment cannot fix it either -
fragment extensions may contribute profiles and colour schemes only, not
keybindings - so README.md gives the settings.json snippet to unbind it by hand
and points at Insert as the alternative. ^V is fine on linux and macOS now that
IEXTEN is cleared.
