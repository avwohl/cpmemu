messages that made the changes, not kept here.  There is no issue tracker; this

- nobody has pressed the keys, on either platform.  tests/win_console.cc writes
INPUT_RECORDs into the console input buffer with WriteConsoleInput and
tests/pty_console.cc writes bytes into a pty master; each is faithful from the
console or the line discipline inward, and each steps past the terminal program
itself.  if Windows Terminal binds ctrl+left for its own use, or Terminal.app or
iTerm binds something, the tests still pass and the user still loses the key.
both harnesses have a --manual mode that runs a hex echo for a person to type
at; someone with a keyboard should do one pass in Windows Terminal, one in a
legacy conhost window, and one in each of Terminal.app and iTerm2.  the machine
the windows side was tested on had no interactive terminal, only a windowless
console.  the macOS side was driven through a pty by a program, which is not a
person either: no real terminal emulator was ever in the loop, so whatever
Terminal.app or iTerm sets in the termios we inherit is still unmeasured.

- nothing on the windows side has been executed since it was rewritten.  three
of the entries that used to be here are done and in CHANGELOG.md: the 0xE0
prefix guess, ctrl+break leaving the console raw, and the missing regression
tests for the two.  os/windows/platform.cc reads INPUT_RECORDs now rather than
calling _getch(), and installs a SetConsoleCtrlHandler; tests/win_console.cc has
five new cases for those changes.  every line of it cross-compiles under
x86_64-w64-mingw32-g++ with no warnings, under -Wextra as well as the -Wall
run_tests.sh requires - and there is no wine and no windows machine here, so not
one line of it has run.  the five new cases have never reported anything at all.
four of them set the console input code page, which nothing in tests/ had ever
done, and expect the bytes the guest gets *after* the & 0x7F at cpmemu.cc:2361 -
so a decision on the eight-bit item below moves those expectations.  the fifth
sends a CTRL_BREAK_EVENT to a process group the harness has to create for the
purpose, or the event would come back and kill the harness.  someone with a
windows box should run tests\win_console.bat once and say what it prints.

- a guest polling BDOS 6 against redirected input still spins on POSIX.
stdin_has_data() (os/linux/platform.cc:280) returns false for anything that is
not a tty, so the read at cpmemu.cc:2349 is never reached, note_console_eof()
never counts, and the 1024-read give-up that ends a windows run cannot fire.
blocked on the item below; it is not fixable on its own.

- the two platforms disagree about whether redirected input is visible to the
polled path, and neither side of it was ever decided.  POSIX returns false from
stdin_has_data() for anything that is not a tty, on purpose, so BDOS 6, BDOS 11
and BIOS CONST never see a pipe or a file there.  windows answers for both
(os/windows/platform.cc:382-402): a pipe through PeekNamedPipe, a file from its
own position.  that means a guest which polls BDOS 11 or BIOS CONST as a break
check while reading its real input through BDOS 1 can take a byte of its own
script on windows and cannot on linux.  the windows half was already like that
for pipes before any of this, so making files match was the smaller of the two
changes available.  whichever way it is settled, three tests move with it: "a
polled read takes nothing from a file" and "... from a pipe" in
tests/pty_console.cc:805,808 against "polled input arrives from a file, not only
from a pipe" in tests/win_console.cc:500 - the same guest printing T on POSIX
and 41 T on windows.

- whether a CP/M guest should see eight bits is undecided, and the decision is
all that is left of the ISTRIP item.  the prose contradiction is fixed: the
comment in os/linux/platform.cc no longer says or implies that the 8th bit
reaches the guest.  it says what is true - clearing ISTRIP keeps the bit through
the line discipline, measured, 128 of 128 high bytes reaching read() unchanged -
and then names the four sites that mask it off: cpmemu.cc:1591 (BDOS 1), :1771
(BDOS 10 buffer store), :2361 (BDOS 6) and :2799 (BIOS CONIN).  so today the
guest gets seven bits: feeding the UTF-8 bytes for e-acute, alpha, pound and
em-dash gives it C3 29 4E 31 42 23 62 00 14, and on the polled path a byte that
masks to 0x00 is dropped entirely because BDOS 6 reads 0 as "no character".
the two answers are: keep the four masks and document that CP/M sees seven bits
here, or drop all four and let the guest have the byte.  the second is not four
line deletions - BDOS 6 would need a way to say "no character" that is not 0,
and the windows code page cases added to tests/win_console.cc encode the masked
answer in their expectations.  nobody has decided which, and nothing here does.

cannot resolve from
anywhere, and Apple's linker prefers it over libqkz80.a in the same -L

because .github/workflows/release.yml:22-31 builds on ubuntu-latest and
ubuntu-24.04-arm only - they are traps for whoever adds a macOS job.  a

com.apple.quarantine`: measured, a build tagged with the quarantine attribute is

work on.  the fourth piece that used to be in this entry, the missing
