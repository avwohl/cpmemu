Todo list.  Open items only - finished work is in CHANGELOG.md and in the commit
messages that made the changes, not kept here.  There is no issue tracker; this
file and github issues on avwohl/cpmemu are the only two mechanisms.

Each item carries a tag for what a machine has to be to pick it up, so a session
on another OS can see at a glance what it can take.  Checks that need a person
at a keyboard are in MANUAL_CHECKS.md, not here.

- [MAC] [WINDOWS] nobody has ever typed at either console harness.  both have a
--manual hex echo; the four terminals to try it in, and what right looks like,
are in MANUAL_CHECKS.md.

- [WINDOWS] the rewritten Windows console path has never been executed.
os/windows/platform.cc reads INPUT_RECORDs rather than calling _getch(), and
installs a SetConsoleCtrlHandler; tests/win_console.cc has five cases for those
- four set the console input code page, one sends a CTRL_BREAK_EVENT to a
process group the harness creates for the purpose - and not one of them has
ever reported anything.  someone with a windows box should run
tests\win_console.bat and say what it prints.  the four code-page cases expect
the bytes the guest gets *after* the & 0x7F, so settling the eight-bit item
below moves their expectations.

- [DECISION] whether a CP/M guest should see eight bits.  four console read
sites in cpmemu.cc mask with & 0x7F - BDOS 1, the BDOS 10 buffer store, BDOS 6
and BIOS CONIN - so the guest gets seven: measured, the UTF-8 for e-acute,
alpha, pound and em-dash reaches it as 43 29 4E 31 42 23 62 00 14, and on the
polled path a byte that masks to 0x00 is dropped outright because BDOS 6 reads 0
as "no character".  the two answers are keep the masks and document that CP/M
sees seven bits here, or drop them and let the guest have the byte.  the second
is not four line deletions: BDOS 6 needs a way to say "no character" that is not
0, and the code-page expectations in tests/win_console.cc move with it.

- [RELEASE] [MAC] a downloaded macOS binary is signed ad hoc and not notarized,
so Gatekeeper refuses it - and from a terminal the refusal has no visible form
at all: measured, the process starts, prints nothing and sits in state SN until
it is killed.  README.md tells the user to xattr -dr com.apple.quarantine, which
is a workaround rather than a fix.  notarizing properly needs a Developer ID
certificate and a notarytool step in the release workflow, and there is neither.

- [RELEASE] the build-macos job in .github/workflows/release.yml has never run
on a GitHub runner.  every shell command in it was extracted from the YAML and
executed by hand on macOS 27 arm64, and each produced what the job expects, but
macos-latest is a different machine with a different Xcode and nothing has
proved the job as a job.  release.yml runs on a push to main as well as on a
release and a workflow_dispatch, so the next push settles it - watch that run
rather than assuming it.
