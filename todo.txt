Todo list.  Open items only - finished work is written up in the commit
messages that made the changes, not kept here.

- the console work still needs running on a mac.  windows is done: the whole
extended-key table, both status calls, the ^C escape hatch and the function 10
line editor are checked on a real console by tests/win_console.cc.  a linux pty
cannot prove the thing the IEXTEN clear was for, because BSD/XNU gates VLNEXT
and VDISCARD on IEXTEN outside the ICANON block, so ^V and ^O want a real mac.
any harness there has to be a pty and not a pipe, because stdin_has_data()
returns false for a non-tty by design and BDOS 6 therefore never sees anything
over a pipe on POSIX.

- nobody has pressed the keys on windows.  tests/win_console.cc writes
INPUT_RECORDs into the console input buffer with WriteConsoleInput, which is
faithful from the console inward but steps past the terminal program itself.
if Windows Terminal ever binds ctrl+left for its own use the tests still pass
and the user still loses the key.  tests/win_console.exe --manual runs the same
hex echo for a person to type at; someone with a keyboard should do one pass in
Windows Terminal and one in a legacy conhost window.  the machine this was
tested on had no interactive terminal, only a windowless console.

- a character whose first byte is 0xE0 is still taken for a special key prefix
when another byte follows it.  measured, console input code page 437: alpha
(U+03B1) alone reaches _getch() as E0 with _kbhit() false, and the guest gets
it - 60 after the usual 7-bit mask.  alpha immediately followed by A gives
E0 41, the 41 is consumed as a scan code, no table entry matches, and the guest
gets neither character.  code page 65001 turns the race into a certainty: U+0E01
encodes as E0 B8 81 and _getch() hands those back one byte at a time.  the fix
is to stop using _getch() and read INPUT_RECORDs directly, which removes the
guess rather than narrowing it; that is a rewrite of the input path, not a patch
to it.

- ctrl+break on windows leaves the console in raw mode.  clearing
ENABLE_PROCESSED_INPUT suppresses ^C but not ctrl+break, and the default handler
ends the process without running atexit, so disable_raw_mode() never runs.
measured: the child exits 0xC000013A and the console mode stays at 0x1A0 instead
of returning to 0x1F7, which leaves the shell with no echo.  a
SetConsoleCtrlHandler that restores the mode and exits would fix it.

- the two platforms disagree about whether redirected input is visible to the
polled path, and neither side of it was ever decided.  POSIX returns false from
stdin_has_data() for anything that is not a tty, on purpose, so BDOS 6 never
sees a pipe there.  windows answers for a pipe, and now for a file as well.
that means a guest which polls BDOS 11 or BIOS CONST as a break check while
reading its real input through BDOS 1 can take a byte of its own script on
windows and cannot on linux.  the windows half was already like that for pipes
before any of this, so making files match was the smaller of the two changes
available.  which behaviour is right was never decided and still is not.

- a guest polling BDOS 6 at end of input spins with nothing to stop it.  the
blocking reads have the "console reads past end of input" guard; the polled path
has no counterpart, because stdin_has_data() answering no is indistinguishable
from a user who has not typed yet.  measured on windows with both an empty pipe
and an empty file: the emulator has to be killed.
