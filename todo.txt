Todo list.  Open items only - finished work is in CHANGELOG.md and in the commit
messages that made the changes, not kept here.  There is no issue tracker; this
file and github issues on avwohl/cpmemu are the only two mechanisms.

- nobody has pressed the keys, on either platform.  tests/win_console.cc writes
INPUT_RECORDs into the console input buffer with WriteConsoleInput and
tests/pty_console.cc writes bytes into a pty master; each is faithful from the
console or the line discipline inward, and each steps past the terminal program
itself.  if Windows Terminal binds ctrl+left for its own use, or Terminal.app or
iTerm binds something, the tests still pass and the user still loses the key.
both harnesses have a --manual mode that runs a hex echo for a person to type
at; someone with a keyboard should do one pass in Windows Terminal, one in a
legacy conhost window, and one in each of Terminal.app and iTerm2.  the machine
the windows side was tested on had no interactive terminal, only a windowless
console.  the macOS side was driven through a pty by a program, which is not a
person either: no real terminal emulator was ever in the loop, so whatever
Terminal.app or iTerm sets in the termios we inherit is still unmeasured.

- a character whose first byte is 0xE0 is still taken for a special key prefix
when another byte follows it.  read_one_key() (os/windows/platform.cc:159) is
still on _getch(), and the guess is the !_kbhit() at :173.  measured, console
input code page 437: alpha (U+03B1) alone reaches _getch() as E0 with _kbhit()
false, and the guest gets it - 60 after the usual 7-bit mask.  alpha immediately
followed by A gives E0 41, the 41 is consumed as a scan code, no table entry
matches, and the guest gets neither character.  code page 65001 turns the race
into a certainty: U+0E01 encodes as E0 B8 81 and _getch() hands those back one
byte at a time.  the fix is to stop using _getch() and read INPUT_RECORDs
directly, which removes the guess rather than narrowing it; that is a rewrite of
the input path, not a patch to it, and it forces five secondary changes
(key-down filter, repeat-count expansion, UTF-16-to-bytes conversion, re-keying
extended_keys[] from CRT scan codes to VK plus a ctrl flag, and widening the
two-slot queue).

- ctrl+break on windows leaves the console in raw mode.  there is no
SetConsoleCtrlHandler anywhere in src/.  clearing ENABLE_PROCESSED_INPUT
suppresses ^C but not ctrl+break, and the default handler ends the process
without running atexit, so disable_raw_mode() never runs.  measured: the child
exits 0xC000013A and the console mode stays at 0x1A0 instead of returning to
0x1F7, which leaves the shell with no echo.  a SetConsoleCtrlHandler that
restores the mode and exits would fix it; the install loop in
os/linux/platform.cc:173-200 is the shape to copy, and its POSIX half is done -
seven kill cases in tests/pty_console.cc hold it to that, and two more hold the
job control pair beside it.

- neither windows bug above has a regression test, because tests/win_console.cc
cannot reach either.  inject_spec()'s single-character branch goes through
VkKeyScanA and casts one byte to WCHAR, so no character above U+00FF can be
named and no code page is set anywhere in tests/; and nothing in the harness
calls GenerateConsoleCtrlEvent.  Both are small additions.

- a guest polling BDOS 6 against redirected input still spins on POSIX.
stdin_has_data() (os/linux/platform.cc:245) returns false for anything that is
not a tty, so the read at cpmemu.cc:2349 is never reached, note_console_eof()
never counts, and the 1024-read give-up that ends a windows run cannot fire.
blocked on the item below; it is not fixable on its own.

- the two platforms disagree about whether redirected input is visible to the
polled path, and neither side of it was ever decided.  POSIX returns false from
stdin_has_data() for anything that is not a tty, on purpose, so BDOS 6, BDOS 11
and BIOS CONST never see a pipe or a file there.  windows answers for both
(os/windows/platform.cc:200-219): a pipe through PeekNamedPipe, a file from its
own position.  that means a guest which polls BDOS 11 or BIOS CONST as a break
check while reading its real input through BDOS 1 can take a byte of its own
script on windows and cannot on linux.  the windows half was already like that
for pipes before any of this, so making files match was the smaller of the two
changes available.  whichever way it is settled, three tests move with it: "a
polled read takes nothing from a file" and "... from a pipe" in
tests/pty_console.cc:778,781 against "polled input arrives from a file, not only
from a pipe" in tests/win_console.cc:422 - the same guest printing T on POSIX
and 41 T on windows.

- the ISTRIP comment in os/linux/platform.cc and the four console read sites
contradict each other.  the comment (:216 and :224) says the 8th bit survives,
and it does survive the line discipline - measured, 128 of 128 high bytes reach
read() unchanged - but all four sites then do `& 0x7F`: cpmemu.cc:1591 (BDOS 1),
:1771 (BDOS 10 buffer store), :2361 (BDOS 6) and :2799 (BIOS CONIN).  feeding
the UTF-8 bytes for e-acute, alpha, pound and em-dash to the emulator gives the
guest C3 29 4E 31 42 23 62 00 14 after masking, and on the polled path a byte
that masks to 0x00 is dropped entirely, because BDOS 6 reads 0 as "no
character".  whether CP/M should see 8 bits is a real question; what is not in
question is that the two statements cannot both stand.

- there is no macOS release path and the pieces that would make one do not work.
`make STATIC=1` (src/makefile:19) cannot link at all: the Apple linker has no
crt0.o and there is no static libc or libc++.  `make shared`
(src/makefile:34,54-55,71) writes libqkz80.so with a bare install name that dyld
cannot resolve from
anywhere, and Apple's linker prefers it over libqkz80.a in the same -L
directory, so a consumer links clean and aborts at exec; `make install-lib`
(makefile:124) then points qkz80.pc at it.  src/CMakeLists.txt:58-70 never sets
CPACK_PACKAGE_FILE_NAME, so cpack names the archive cpmemu-4.6.0-Darwin.tar.gz
with no architecture, and the same is true of every non-Windows platform, so
linux amd64 and arm64 collide identically.  none of this breaks CI today,
because .github/workflows/release.yml:22-31 builds on ubuntu-latest and
ubuntu-24.04-arm only - they are traps for whoever adds a macOS job.  a
downloaded binary would also need notarizing or the user needs `xattr -d
com.apple.quarantine`: measured, a build tagged with the quarantine attribute is
refused by spctl and killed on exec.

- the kill cases in tests/pty_console.cc fail intermittently under load and
nobody has diagnosed it.  measured on a 2-core linux box: "the terminal is put
back on a quit" failed once in 40 runs of the harness with 32 spinning
processes for company, reporting "the emulator had to be killed: it never
finished", and none in 8 unloaded runs; a --zex run on the same host hit "the
terminal is put back on a hangup" the same way.  not a regression - the seven
kill cases are byte for byte what fa2a6b4 has and the console work did not
touch them.  the suspect is a shared budget: run_case() spends the same
timeout_ms (10000 for these) first spinning until tcgetattr shows ICANON clear
(tests/pty_console.cc:430-438) and then waiting for the child to exit (:474), so
a slow start eats the wait and the case reports a hang that never happened.
that is a guess, not a measurement.  until it is understood, a green
run_tests.sh is evidence and not a guarantee, and "0 failed" should not be
quoted as a property of the suite.

- the 8080 exerciser is in the tree three times over and only one copy is run.
tests/8080EXM.COM is wired into run_tests.sh --zex now and passes 25 of 25
groups; tests/8080exer.com is run by nothing, and tests/8080/ holds a third set
(8080exm.com and 8080exer.com, byte for byte the same two files, plus
8080pre.com) with the .mac sources and a README of its own.  8080exer.com is the
same 25 tests with "OK" where 8080exm prints the CRC, so it is duplication
rather than coverage.  8080pre.com is not: it is the preliminary test, it runs
in well under a second, and it passes today - `cpmemu --8080
tests/8080/8080pre.com` prints "8080 Preliminary tests complete".  worth running
the preliminary one in the default suite, since it is cheap enough not to need
--zex, and worth deciding which copy of the rest is canonical and deleting the
others.

- src/qkz80*.{cc,h} is compiled directly by three other emulators and nothing
here says so.  README's Related Projects lists them; what it does not record is
that they do not depend on a cpmemu *release* - they build these source files
out of a sibling working tree, so an edit to qkz80.cc lands in all three on
their next build, with no version gate and no notification:
  - ioscpm    - 11 symlinks in iOSCPM/Core/ pointing at ../cpmemu/src/qkz80*
  - z80cpmw   - z80cpmw.vcxproj compiles $(SolutionDir)..\cpmemu\src\qkz80*
  - romwbw_emu- src/makefile falls back to ../../cpmemu/src for headers and
    libqkz80.a when pkg-config misses, and its release.yml clones
    avwohl/cpmemu at default-branch HEAD with no tag or SHA
  the last of those means a cpmemu commit can break a romwbw_emu release with
  nobody touching that repo.  06262ff is the worked example of the mechanism
  working quietly in the good direction: it added QKZ80_NO_TRACE and all three
  picked it up without being told.  worth a line in README, and worth checking
  the three before changing qkz80's public surface.  they compile with -Wall and
  ioscpm builds as Objective-C++ for arm64, which is stricter than this repo's
  own build in places.
